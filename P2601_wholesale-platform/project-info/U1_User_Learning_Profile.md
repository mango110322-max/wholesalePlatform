## 沟通偏好

讨论技术实现时，应优先使用业务链路来解释，而不是直接堆框架名。

推荐解释方式：

```text
卖家端页面
  ↓
后端 Controller 接收请求
  ↓
Service 处理业务规则
  ↓
Mapper/DAO 操作数据库
  ↓
MySQL 表保存数据
```

对于 `wholesalePlatform`，优先围绕具体场景解释：

- 卖家新增商品如何保存到数据库
- 商品审核状态如何影响买家端展示
- 库存变化如何影响商品可售状态
- 询盘如何从买家端进入卖家端待处理列表

避免一开始直接使用过多抽象概念，例如完整微服务架构、复杂权限体系、消息队列、缓存、分布式事务等。可以先提到它们是后期能力，但不要作为 MVP 第一阶段重点。

## 当前适合的项目推进方式

当前不建议一开始直接做完整三端商城。更适合先搭一条最小纵向链路：

```text
卖家端新增商品页面
  ↓
POST /api/seller/products
  ↓
ProductController
  ↓
ProductService
  ↓
ProductMapper
  ↓
product 表
```

第一阶段目标不是把所有功能做完，而是先理解并跑通：

- 页面如何提交数据
- 后端如何接收数据
- 业务规则在哪里处理
- 数据如何写入数据库
- 页面如何再次查询并展示数据

## 补充观察：快捷指令系统体现出的工程能力

记录时间：2026-06-14

Allen 使用 iOS 快捷指令搭建了一个个人自动化系统，并将 `main()` 绑定到 Action Button 作为统一入口。该系统虽然不是传统代码项目，但已经体现出较明显的工程化思维：

- 能把 `main()` 设计成入口和路由层，通过第一层菜单进入计时、查询、付款、记录、喝水等模块。
- 能继续拆出二级菜单，例如“记录”下面再分发到午睡、睡觉、体重、上班、散步等具体动作。
- 能按职责拆分快捷指令文件夹，例如执行层、数据获取、Util、备份等，接近 Controller、Service、Query Service、工具函数的分层思路。
- 能使用本地 JSON 文件保存事件词典、上次查询结果和菜单回显数据，理解本地状态文件相当于轻量数据源或缓存。
- 能根据数据特性选择不同读取策略：计时器剩余时间这类强即时数据实时查询；饮水量、体重等查询较快的数据现场读取；查词结果这类稳定且可复用的数据写入 JSON，下次快速回显。
- 能感知入口性能对用户体验的影响，并主动避免在 `main()` 中执行过多慢查询，把部分慢查询转为提前计算、持久化或读取缓存。
- 能理解菜单项不只是命令入口，也可以承载实时或近实时状态摘要，形成类似 Command Palette + Dashboard 的交互模式。

这说明 Allen 虽然还未系统进入 Spring Boot、数据库和前后端联调阶段，但已经具备一部分软件开发中的模块化、状态管理、缓存策略、入口性能优化和分层设计意识。

项目沟通时，可以更大胆地借用以下类比帮助理解后端结构：

```text
Action Button / main()
  ≈ 应用入口 + Controller / Router

执行层快捷指令
  ≈ Application Service / Use Case

数据获取快捷指令
  ≈ Query Service / Adapter

Util 快捷指令
  ≈ 工具函数 / Helper

本地 JSON 文件
  ≈ 本地数据源 / 缓存 / Read Model
```
